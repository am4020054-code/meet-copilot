# Задержка подсказок: замеры и бесплатные правки

Денис, это разбор того, почему подсказки приходят медленно, и что можно сделать без платного
аккаунта. Раздел «Задачи для Codex» написан так, чтобы его можно было отдать агенту как есть.

## Коротко

- Модель перечитывает весь контекст на каждый запрос: кеша нет, поле `cached_tokens` в ответах
  шлюза всегда 0. Время до первого токена растёт вместе с объёмом документов.
- На бесплатном аккаунте из 65 моделей шлюза доступны только `gemma-4-31b` и `qwen3.5-4b-32k-fast`.
  Модели с кешированием (Claude, Gemini, GPT) отвечают «нет доступа».
- «В контексте только 12 вопросов» — следствие загрузчика: он молча пропускал подпапки и всё, кроме
  `.md` и `.txt`.
- Лимит, в который мы упёрлись, — лимит шлюза на токены в минуту: 300 000 для `gemma-4-31b`.

## Как мерили

Контекст — 10 файлов документации реального SaaS-продукта на русском, 139 КБ (32 тыс. токенов).
Шесть технических вопросов на английском из `bench/questions.txt`. Запросы те же, что шлёт сервер
(`hints.gateway_messages`, тот же `max_tokens`). Аккаунт бесплатный. По 3–6 запросов на строку,
один прогон, поэтому это порядок величин, а не точные цифры.

```sh
python bench/latency.py --context <папка> [--real] [--show]
python bench/route_probe.py --context <папка> --show
```

## Что получилось до правок

| Контекст | Токенов на входе | Первый токен | Первый текст на экране | Вся карточка |
|---|---|---|---|---|
| пустой | 0,6 тыс. | 1,4 с | 1,4 с | 3,6 с |
| 5 КБ | 2,1 тыс. | 1,4 с | 1,8 с | 4,1 с |
| 47 КБ | 13 тыс. | 3,0 с | 3,7 с | 4,3 с |
| 139 КБ | 32 тыс. | 9,5 с | 11,2 с | 13,8 с |

«Первый текст на экране» — событие `answer_core`: клиент показывает ответ, когда строка `SAY`
дописана целиком.

Из чего складывается задержка:

1. Чтение контекста моделью: примерно 4 тыс. токенов в секунду. На 32 тыс. токенов это ~8 с.
2. Новое TLS-соединение на каждый запрос: 0,5–1,2 с.
3. `SAY` выходил длинным (50–75 слов, иногда со списком), а экран ждёт конца строки: ещё ~1,7 с.
4. На один вопрос уходит до четырёх запросов (две ранние подсказки, ответ, «следующий шаг»),
   каждый с полным контекстом. При 32 тыс. токенов это два вопроса в минуту, дальше 429 и пауза 60 с.
5. Ранняя подсказка на полном контексте готова через ~12,6 с, то есть после конца реплики.
6. Раз в 15–20 запросов шлюз отвечает через 14–16 с при любом размере контекста. После 4,5 минут
   простоя первый запрос был обычным (1,2 с), так что это не «холодный старт».

## Что сделано в этой ветке

| Правка | Где | Эффект |
|---|---|---|
| Пропущенные файлы и папки видны в статусе, на экране и в консоли | `hints.load_bundle`, `server.py` | Больше нельзя не заметить, что документы не загрузились |
| Соединение со шлюзом открывается заранее | `hints.WarmConnection`, `gateway_stream` | −0,5…1,2 с на каждый запрос |
| `SAY` — одна строка, до двух коротких предложений | `hints.FORMAT` | 20–32 слова вместо 50–75; строка дописывается раньше |
| Ранние подсказки и «следующий шаг» отключаются, если контекст больше 24 КБ | `public/app.js` | Один запрос на вопрос вместо четырёх |

Поведение загрузчика не менялось: подпапки и другие форматы по-прежнему не читаются, теперь об
этом сообщается. Тесты: `python -B -m unittest discover -s tests` и `node tests/core.mjs` проходят
так же, как до правок.

| Контекст | Первый текст: до → после | Вся карточка: до → после |
|---|---|---|
| 5 КБ | 1,8 → 1,0–1,2 с | 4,1 → 1,9 с |
| 139 КБ | 11,2 → 8,4 с | 13,8 → 10,5 с |

Вывод: на полном контексте правки дают около трёх секунд, но 8 с — всё ещё долго. Оставшееся
время — чтение контекста моделью, и на этой модели его можно убрать только уменьшив контекст.

## Эксперимент: отбор разделов под вопрос

`bench/route_probe.py`, в сервер не встроено. Документы режутся по заголовкам (149 разделов).
Шаг 1: модель видит только оглавление и называет до шести разделов. Шаг 2: обычный запрос
подсказки, но в контексте только эти разделы.

| | Весь контекст (после правок) | Отбор разделов |
|---|---|---|
| Первый текст на экране | 8,4 с | 3,8 с |
| Вся карточка | 10,5 с | ~5,2 с |
| Токенов на вопрос | 32 тыс. | ~7 тыс. (5,1 тыс. оглавление + 1,2–2,8 тыс. разделы) |
| Вопросов в минуту по лимиту | ~9 | 15 (упирается уже в 30 запросов в минуту) |

Цена — качество. Из шести ответов два стали беднее: про коммунальные платежи модель потеряла, что
поддерживаются оба способа расчёта, про резервные копии сказала «в документах нет», хотя с полным
контекстом находила упоминание. Остальные четыре по сути совпали.

## Задачи для Codex

Каждую задачу можно делать отдельно. Проверка скорости — `bench/latency.py --real` до и после.

1. **Показать первое предложение сразу.** Сервер уже шлёт событие `say`, когда готово первое
   предложение `SAY`; клиент в `ask()` только пишет его в журнал (`say_preview`). Показать его на
   экране как черновик и заменить текстом из `answer_core`. Готово, когда первое предложение видно
   раньше конца строки `SAY`, а при отмене запроса черновик исчезает.

2. **Встроить отбор разделов** по образцу `bench/route_probe.py`, включая его только когда контекст
   больше порога (`HEAVY_CONTEXT_BYTES`). Требования: оглавление строится один раз при старте;
   файл с главными фактами (например, первый по алфавиту) добавляется в контекст всегда; если шаг
   отбора вернул пусто или ошибку — отвечать по главному файлу и писать об этом в `NOTE`;
   выбранные разделы пишутся в журнал. Готово, когда на контексте ~140 КБ первый текст появляется
   быстрее 4,5 с в медиане по `bench/questions.txt`.

3. **Запускать отбор разделов по незаконченной фразе.** Механизм ранней подсказки
   (`considerPreliminary`) уже ловит момент, когда вопрос понятен до конца реплики. Вместо ранней
   подсказки запускать в этот момент шаг отбора, чтобы к концу реплики оставался только шаг ответа
   (~1,5–2 с). Если финальная реплика заметно отличается от фрагмента, отбор повторяется.

4. **Сжать оглавление.** Сейчас это 17 КБ (5,1 тыс. токенов) и ~1,7 с на шаг отбора. Проверить
   вариант без первых слов раздела (`--preview 0`) и вариант с заранее сгенерированным
   однострочным английским описанием каждого раздела. Смотреть и на время, и на то, какие разделы
   выбираются.

5. **Свой доступ к GPT вместо шлюза.** Запрос уже в формате chat completions, так что замена — это
   адрес, заголовок авторизации и имя модели: вынести их в настройки. У OpenAI длинный одинаковый
   префикс запроса кешируется автоматически, а документы в системном сообщении уже стоят первыми,
   то есть префикс стабилен. Мы это не проверяли: нужен ключ API OpenAI, подписки ChatGPT для
   этого недостаточно. Если ключа нет, вариант — вызывать `codex exec` как у нас вызывается
   `claude -p`; запуск процесса на каждый вопрос добавит задержку, её надо замерить тем же
   `bench/latency.py`. Сравнить с отбором разделов на тех же шести вопросах и оставить то, что
   быстрее при полном контексте.

6. **Не терять документы.** Сейчас загрузчик только сообщает о пропущенном. Решить, читать ли
   подпапки и `docx`/`pdf`; если нет — не запускать живой режим, пока в статусе есть пропущенные
   файлы, без явного подтверждения.

## Чего замеры не показывают

- Живой звук из Meet и задержку распознавания конца реплики: мерился только путь подсказки.
- Другие модели шлюза: на бесплатном аккаунте они закрыты.
- Устойчивость цифр: один прогон, одно время суток, выбросы провайдера по 14–16 с.
- Интерфейс: правка в `public/app.js` проверена только синтаксически, в браузере не запускалась.
